### 我的解法

```cpp
class Solution {
public:
    vector<vector<int>> updateMatrix(vector<vector<int>>& mat) {

        int m = mat.size();
        int n = mat[0].size();

        int Xa[] = {-1, 0, 1, 0};
        int Ya[] = {0, -1, 0, 1};

        vector<vector<int>> res(m, vector<int>(n, -1));
        queue<pair<int,int>> que;

        for(int i = 0 ; i < m ; i++){
            for(int j = 0; j < n ; j++){
                if(mat[i][j] == 0){
                    res[i][j] = 0;
                    que.push({i,j});
                }
            }
        }

        while(!que.empty()){

            auto [r ,c] = que.front();

            for(int i = 0; i <= 3 ; i++ ){
                if( r + Xa[i] < 0  || r + Xa[i] >= m ||
                    c + Ya[i] < 0  || c + Ya[i] >= n   ){
                        continue;
                    }else{
                        if(res[r+Xa[i]][c+Ya[i]] == -1){
                            res[r+Xa[i]][c+Ya[i]] = res[r][c] + 1;
                            que.push({r+Xa[i], c+Ya[i]});
                        }
                    }
            }

            que.pop();

        }

        return res;
    }
};
```

- 時間複雜度：O(m×n)
- 空間複雜度：O(m×n)

### 解題過程

#### 虛擬碼階段：從 DFS 轉向多起點 BFS 的推導過程

一開始想用 DFS（往外看鄰近的 1，取最小值 +1，加上記憶化空間避免重複計算）。經提問點出兩個關鍵問題：
1. **循環依賴**：兩個相鄰、都還沒確定答案的 `1` 可能互相依賴對方的值，DFS + 記憶化會在兩者之間無限繞圈，跟 Climbing Stairs 那種「子問題永遠比自己小」的記憶化情境本質不同
2. 自己描述的「先處理 0、再處理貼近 0 的 1、再處理更遠的 1」這種逐層順序，跟 DFS「往一個方向鑽到底」的走法本質上不同，是按層次擴散的順序

自己想通要轉向 BFS 後，一開始的設計還停留在「重新掃整個矩陣找上一輪剛設定的格子」這種手動模擬分層的方式，且用「之後如果有更小的值就覆蓋」處理不確定性。經提問確認：只要嚴格按照「上一輪已確定答案的格子」去推算「這一輪還沒確定的格子」，新算出的值不會被之後的資料覆蓋——這正是多起點 BFS 的正確性保證。進一步確認可以用 `queue` 記住「下一輪要處理的格子」，不用每輪重新掃整個矩陣。

#### 程式碼階段：六輪除錯

**C 類（語法/型別）**：
1. `vector<vector<int>> res;` 沒有先給定大小就直接 index 賦值，改成 `vector<vector<int>> res(m, vector<int>(n, -1));`
2. `res[r+Xa[i], c+Ya[i]]` 用逗號而非兩層 `[][]`，改正為 `res[r+Xa[i]][c+Ya[i]]`（跟 `vector.md` 記錄的多維索引問題同類）
3. `que.push([...])` 用方括號而非大括號建立 `pair`，改正為 `que.push({...})`

**A 類（邏輯）**：
4. 邊界檢查用 `break` 而非 `continue`：某個方向一超出邊界就直接跳出整個 for 迴圈，導致其餘方向完全沒被檢查。用 `mat=[[0,1],[1,1]]` trace 出，(0,0) 這個角落格子的第一個檢查方向（往上）就超出邊界，`break` 直接跳出，且因為 `pop()` 只寫在 in-range 分支裡，這一輪連 `pop()` 都沒執行到，導致 `while` 迴圈無窮迴圈（一直讀到同一個沒被移除的 front）
5. `que.pop()` 原本放在 for 迴圈內部，每個方向都可能呼叫一次，跟只讀了一次的 `front()` 不對應。改成迴圈外，每輪 while 只 pop 一次
6. 邊界判斷用 `> m`/`> n`，合法索引範圍上限應該是 `size-1`，用 `mat` 大小 `m=2` 的例子 trace 出 `row=2`（不存在的索引）沒被邊界檢查擋下，改成 `>= m`/`>= n`

### 1️⃣ 語法概念

- `vector<vector<int>>` 宣告後要用建構子給定大小（`vector<vector<int>>(m, vector<int>(n, 預設值))`），不能宣告成空的就直接用 index 賦值
- `queue<pair<int,int>>` 建立元素要用大括號 `{}`，不是方括號 `[]`
- `que.front()` 只是讀取，不會移除元素；`que.pop()` 才是移除，且要放在正確位置（一輪只呼叫一次，對應剛剛讀到的那個元素）

### 2️⃣ 邏輯與複雜度

- O(m×n) 時間、O(m×n) 空間，是這題最優解——每個格子只會被放進 queue 一次、展開一次
- **多起點 BFS 的核心正確性保證**：所有起點必須一次性放進 queue、同時展開，不能分開跑，否則某個格子可能先被較遠的起點走到並標記，導致更近的起點之後展開時被跳過，得到錯誤的偏大距離
- 邊界檢查用 `continue` 而非 `break`：多方向檢查裡，單一方向超出邊界只該跳過那個方向，不是中斷整個檢查

### 3️⃣ 演算法 / 資料結構盲點

- 第一次遇到「多節點互相依賴最短距離」的題型，直覺想用 DFS + 記憶化，沒有意識到這種循環依賴跟一般記憶化遞迴（子問題單向變小）的本質差異，之後遇到「找最短距離/最少步數」類題目，先檢查會不會有循環依賴，有的話優先考慮 BFS 而非 DFS
- 第一次用「多起點」BFS（不是單一起點展開），核心差異只在初始化階段把所有起點一次放進 queue，其餘邏輯跟一般 BFS 完全一樣，已整理進新概念卡 `bfs.md`
- `front()`/`pop()` 職責分離、`continue`/`break` 差異、邊界索引 `>=` vs `>` 這幾個問題同時出現在同一輪除錯，顯示這是第一次寫 queue-based BFS 手動樣板時，多個「小地方」都還沒建立肌肉記憶，跟之前反覆出現的「迴圈狀態管理」是相關但更細節層級的新樣態
