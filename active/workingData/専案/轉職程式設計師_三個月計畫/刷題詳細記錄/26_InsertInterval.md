### 我的解法

```cpp
class Solution {
public:
    vector<vector<int>> insert(vector<vector<int>>& intv, vector<int>& nIntv) {

        vector<vector<int>> res;
        bool trigger = false;

        if(intv.empty()){
            res.push_back(nIntv);
            return res;
        }

        for(int i = 0; i < intv.size() ; i++){
            if(nIntv[0] > intv[i][1]){
                res.push_back(intv[i]);
            }else if(nIntv[0] <= intv[i][1] && nIntv[1] >= intv[i][0]){
                nIntv[0] = min(intv[i][0], nIntv[0]);
                nIntv[1] = max(intv[i][1], nIntv[1]);
            }else{
                if(!trigger){
                    res.push_back(nIntv);
                    trigger = true;
                }
                res.push_back(intv[i]);
            }
        }

        if(!trigger){
            res.push_back(nIntv);
            trigger = true;
        }

        return res;
    }
};
```

- 時間複雜度：O(n)
- 空間複雜度：O(n)（輸出陣列，不含輸入本身）

### 解題過程

#### 虛擬碼階段：第一版設計繞了遠路，且「被示範」不等於「真的懂」

一開始設計了一套「先用二分掃描找出 `nIntv` 該插入的位置索引、分別處理左右端點合併、記錄要刪除的範圍、最後用迴圈刪除中間區間」的做法，包含多層巢狀 `if`、`delMinCount`/`delMaxCount` 等變數。這套設計本身用範例 trace 出兩個問題：
1. 插入點判斷邏輯只處理了「找到 i」的情況，沒考慮 `nIntv` 比所有既有區間都小時 `i-1=-1` 的邊界，會存取不存在的陣列索引
2. 整體設計層層疊疊，複雜度高、容易在單一分支裡藏 bug

主動要求提供思考方向，得到「三態分類」（左邊不重疊／重疊要合併／右邊不重疊）的具體案例演示後，坦白指出這已經是給答案而非引導。**事後補充的關鍵回饋**：即使拿到這份具體案例演示，當下並沒有真正理解、吸收「為什麼要這樣分」，最終是自己額外拿紙筆把所有情況重新跑過一遍，才真正抓到訣竅——直接被示範案例，跟自己動手 trace 一遍，對這次而言是兩件不同的事，後者才是真正建立理解的環節。三小時裡有相當比例的時間花在這個從「看懂案例」到「自己內化」的過程，不是單純的除錯時間。

#### 程式碼階段：四輪除錯，vector 索引維度是最大的卡點

**事後補充**：這題語法上花費最多時間的地方，是 `vector` 兩個不同維度（`intv` 是 `vector<vector<int>>`，`nIntv` 是 `vector<int>`）之間互相取值、比對、代入的操作，一直沒能一次寫對，撞牆很久，最後是把整段索引邏輯全部砍掉重寫，才一次處理好。

1. **型別誤用**：一開始把 `nIntv`（`vector<int>&`，單一區間 `[start,end]`）當成 `vector<vector<int>>` 操作，寫成 `nIntv[0][0]`、`nIntv[0][1]`，多索引了一層，編不過。改成直接用 `nIntv[0]`、`nIntv[1]`
2. **三態判斷條件方向錯誤（連續兩次）**：第一次合併條件只單向比較（`intervals[i][1] >= newIntervals[0][0]`），漏了另一個方向，用 `[6,9]` 誤判成跟已合併過的 `[1,5]` 重疊；第二次直接換成另一個不相干的判斷式（完全不重疊的條件），導致最基本的重疊案例都判斷不出來。最終確認重疊判斷需要**兩個方向同時成立**（`nIntv[0]<=intv[i][1] && nIntv[1]>=intv[i][0]`），用 `&&` 合併
3. **三個狀態用獨立 `if` 各自判斷，導致同一輪可能觸發不只一個分支**：`i=0` 那一輪「合併」跟「該把 nIntv 放進答案」同時成立，多推播了一次已經被合併掉的舊區間。改成 `if / else if / else`，讓三個狀態互斥，同一輪只會執行其中一種動作
4. **收尾動作只寫在迴圈內，漏了迴圈跑完都沒觸發的情況**：用 `intv=[[1,2],[3,5]]`, `nIntv=[4,10]` 這種「一路合併到最後、從沒進入『右邊不重疊』分支」的例子 trace 出：`nIntv` 合併完後從未被放進 `res`。補上迴圈外「如果 `trigger` 還是 `false`，最後補一次 push」解決

### 1️⃣ 語法概念

- 呼叫函式前要先確認每個參數的實際型別，`vector<int>` 跟 `vector<vector<int>>` 索引層數不同，設計虛擬碼前先看清楚函式簽名，避免整段邏輯照錯的型別想

### 2️⃣ 邏輯與複雜度

- O(n) 時間、O(n) 空間，是這題最優解——單一掃描，不需要額外找插入點、不需要事後刪除區間
- **兩個區間「有重疊」的判斷需要同時滿足兩個方向的條件**（`A.start<=B.end && B.start<=A.end`），只檢查其中一個方向會誤判
- **一組資料如果邏輯上該分成互斥的幾種狀態，要用 `if/else if/else` 而不是各自獨立的 `if`**，否則同一輪可能意外觸發不只一個分支，這是本題除錯過程中最核心的一個修正

### 3️⃣ 演算法 / 資料結構盲點

- 第一版設計（找插入點 + 記錄刪除範圍）比正確方向複雜很多，是「沒有先想清楚能不能用一次線性掃描搭配狀態分類解決，而是先設計了偏向手動定位/修補的方案」的盲點，之後遇到「排序好的區間/陣列要插入新元素並可能合併」類題目，優先考慮單一掃描 + 狀態分類，而不是先找索引再修補
- **迴圈跑完後可能還有一個收尾動作沒被觸發**：這次用 `trigger` 布林值 + 迴圈外補一次判斷解決，跟 Add Binary（67 題）「把收尾動作塞進迴圈條件本身」是同一類問題的不同解法，這題因為收尾動作（push nIntv）只需要做一次、且判斷時機明確，用布林旗標 + 迴圈外檢查更直覺
