### 我的解法

```cpp
class Solution {
public:
    vector<vector<int>> threeSum(vector<int>& nums) {

        vector<vector<int>> rtn;
        int rltSum ;
        int pinIdx;
        int left;
        int right;

        if(nums.size() == 0){
            return rtn;
        }

        sort(nums.begin(), nums.end());

        for(int idx = 0; idx < nums.size() ; idx++){

            if(idx>0 && nums[idx] == nums[idx-1]){
                continue;
            }

            pinIdx = idx;
            left = pinIdx + 1;
            right = nums.size() - 1;
            rltSum = 0-nums[pinIdx];

            while(left < right){
                if(rltSum == nums[left]+nums[right] ){
                    rtn.push_back({nums[pinIdx], nums[left], nums[right]});
                    left++;
                    while(left < right && nums[left] == nums[left-1]){
                        left++;
                    }
                }else{
                    if(rltSum > nums[left]+nums[right]){
                        left++;
                    }else{
                        right--;
                    }
                }
            }

        }

        return rtn;
    }
};
```

- 時間複雜度：O(n²)
- 空間複雜度：O(1)（不含輸出）

### 解題過程

這題花費時間長，經歷了完整的四階段引導，是目前記錄過最完整的一次除錯歷程。

#### 階段 1：釐清重複的判斷基準

主動確認「重複」是指數值內容而非索引（`[-1,-1,-1,2]` 不管取哪三個索引組合，都算同一組答案），確認題目要求無誤。

#### 虛擬碼階段：從暴力枚舉到排序 + 雙指標

一開始提出「雙迴圈走訪前兩個值 + 查詢第三個值是否存在 + 用容器記錄已見過的組合去重」，主動意識到這樣時間成本會爆炸（近似 O(n²×m)）。經提示回想起雙指標技巧（曾用於 Merge Two Sorted Lists），一開始誤以為是二分法，經澄清雙指標是「兩個指標從陣列兩端同時往中間逼近」，不是「砍半搜尋」。

推導雙指標收斂邏輯時，一度誤以為「找到目標值就整個跳出搜尋」，用具體例子（`[-1,-1,0,1,2,3]` 固定 `-1` 之後，範圍內其實有兩組解 `[-1,-1,2]` 與 `[-1,0,1]`）點出提早跳出會漏解，修正成「找到後移動其中一方繼續收斂，直到指標交錯才真正跳出」。

#### 程式碼階段：多輪除錯

**A 類（邏輯，逐項用具體例子 trace 揪出）**：

1. `while(left >= right)`：條件方向整個寫反，導致迴圈一次都不會執行，`formula` 形同虛設。改成 `while(left < right)`
2. `right = nums.size()`：合法索引上限應為 `size()-1`，改正
3. 外層迴圈跳過重複值時把 `continue` 誤改成 `break`：用 `[-5,-5,-4,-3,7]` trace 出，`idx=1` 觸發 `break` 後，`idx=2`（找到答案 `[-4,-3,7]` 所需的關鍵一步）完全不會被執行，導致漏解。改回 `continue`
4. 嘗試用 `rtn.find(...)` 事後比對去重：`vector` 沒有 `.find()` 成員函式（只有關聯式容器才有），且邏輯方向也錯了（該是「沒找到才加入」）。經引導改用「在雙指標收斂過程中主動跳過重複值」取代事後比對，從根本上避免產生重複
5. `while(nums[left++] == nums[left])`：同一運算式裡先修改 `left`（`left++`）又讀取它（`nums[left]`），C++ 未規定 `==` 兩邊求值順序，屬於未定義行為。拆成獨立敘述句 `while(left < right && nums[left] == nums[left-1])`
6. 跳過重複值時比較方向錯誤，用 `nums[left+1]` 而非 `nums[left-1]`：用 `[-2,-2,0,0,2,2]` trace 出 `nums[left+1]` 問的是「後面還有沒有一樣的」，不是「跟剛剛用過的值是否相同」，導致重複組合沒被正確跳過，改用 `left-1`
7. 手誤把 `right--` 打成 `right++`（自己發現並訂正）：會讓右指標往超出陣列的方向移動

**其他討論（不是 bug，是設計優化）**：

- 確認找到目標值後不需要同時移動 `left++` 跟 `right--`，只動一邊即可，另一邊靠正常的比較邏輯自然接手
- 參考別人的解法後，發現「尾段判斷」（`idx > size-2` 就 `break`）完全不需要，`while(left<right)` 本身已經涵蓋這個邊界；同時發現自己把 `pinIdx`、`left`、`right`、`rltSum` 設計成成員變數、外加獨立 `formula()` 函式是多餘的，改成全部區域變數、單一函式，與 K Closest Points to Origin（第 28 題）同一類「不需要用成員變數卻用了」的盲點，第 2 次出現，已登記進跨題目盲點彙總

### 1️⃣ 語法概念

- 排序用 `sort(nums.begin(), nums.end())`，直接對現有 `vector` 原地排序，不需要換容器
- `vector` 沒有 `.find()` 成員函式，只有 `map`/`set`/`unordered_map`/`unordered_set` 這類關聯式容器才有；`vector` 要查詢用 `std::find`（`<algorithm>`，吃 iterator）
- 同一運算式裡不能一邊修改一個變數、一邊又讀取它（`nums[left++]==nums[left]` 這種寫法是未定義行為），要拆成獨立敘述句

### 2️⃣ 邏輯與複雜度

- O(n²) 時間（外層 n、內層雙指標攤還 O(n)）、O(1) 額外空間，是這題的標準最優解
- 雙指標收斂時「找到目標值不能直接跳出，要移動一方繼續」，跟「陣列本身重複值需要在收斂過程中主動跳過（比較方向是跟『剛用過的值』`left-1`，不是『還沒用過的下一個值』`left+1`）」是這題兩個最核心的正確性關鍵
- 先確認迴圈本身的條件（`while(left<right)`）有沒有天然涵蓋邊界情況，再決定要不要額外寫特殊判斷，不必要的「尾段判斷」拿掉後程式碼更精簡

### 3️⃣ 演算法 / 資料結構盲點

- 對「雙指標」和「二分法」兩個技巧的適用情境混淆了一次（誤以為是二分法），兩者都是靠陣列排序後的性質加速，但雙指標是「兩端同時往中間逼近找一對數字」，二分法是「找單一個值、每次砍半」，之後遇到類似情境要先確認要找的是「一對/多個數字的組合」還是「單一個值」
- 事後比對去重（`rtn.find`）在效率跟語法上都比「收斂過程中主動跳過重複」差，之後遇到「排序後的資料要去重」，優先考慮利用排序本身的相鄰特性跳過重複，而不是額外開容器事後比對
