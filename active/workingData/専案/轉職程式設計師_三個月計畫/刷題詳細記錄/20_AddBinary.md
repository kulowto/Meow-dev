### 我的解法

```cpp
class Solution {
public:
    string addBinary(string A, string B) {

        string R;
        int a,b,r,abCount,abXor;

        for (int i=0; i < max(A.length(), B.length()); i++){

            if ( i >= A.length()){
                a = 0;
            }else{
                a = A[A.length()-i-1]-'0';
            }

            if (i>=B.length()){
                b = 0;
            }else{
                b = B[B.length()-i-1]-'0';
            }

            if(i == 0){
                r = 0;
            }else{
                if(abCount+r >= 2){
                    r = 1;
                }else{
                    r = 0;
                }
            }

            abCount = a+b;
            abXor = a^b;
            R += to_string(abXor^r);

            if (i == max(A.length(), B.length())-1){
                if(abCount+r>=2){
                    R += "1";
                }
            }
        }

        reverse(R.begin(), R.end());
        return R;
    }
};
```

- 時間複雜度：O(max(n,m))
- 空間複雜度：O(max(n,m))（輸出字串大小）

### 解題過程

#### 虛擬碼階段：進位規則反覆修正

一開始想用兩個 LIFO 容器裝 A、B，經提問後自己發現字串本身就能直接用 index 從尾端存取，不需要額外複製進 stack。

進位判斷規則反覆試錯：一開始把 `sum = A^B^R` 誤用來同時算進位，被具體反例（`A=1,B=1,R=0` 這一位應該進位，但 XOR 算出 0）點出「sum 公式」跟「進位公式」不是同一條，後來確認進位規則是「A、B、R 三者中至少兩個是 1」（等同 `abCount+r>=2`）。

還提出一個「A 或 B 有一方沒資料時可以做最後優化」的想法，討論後確認主迴圈本身已經自然涵蓋這個情況（用 0 補位），這個分支不需要額外寫。

#### 程式碼階段：三輪 bug

1. 索引 `A[length()-i]` 少減 1，超出邊界，改成 `A[A.length()-1-i]`
2. `r = abxor ^ r` 又用回 XOR 算進位（跟虛擬碼階段修正過的錯誤重複發生在程式碼層），且進位條件不成立時沒有 `else` 重置 `r = 0`，導致進位錯誤地持續傳遞到後面的位數。用 `A="110010", B="001010"` trace 到 `i=3` 抓出：`i=2` 這一位算完不該進位，但因為沒 reset，`r` 一直維持前一輪的 `1`
3. 最嚴重的一次：`a, b, r, abCount, abXor` 宣告在 `for` 迴圈**裡面**，導致 `abCount`、`r` 每輪都是全新未初始化的變數，跨輪根本沒有真正被保留下來（讀取到未定義行為）。用 `A="11", B="1"` trace 抓出：`i=1` 讀到的 `abCount`、`r` 不是 `i=0` 算出來的值。改成宣告在迴圈外面才解決
4. 兩個打字錯誤：`if (i = max(...)-1)` 少打一個 `=`（賦值蓋掉 `i` 而非比較）、`a.lenght()` 拼字錯誤

修好後送出測試通過，事後看到別人的兩種寫法，都用「把 a、b、carry 當數字直接相加，`%2` 取輸出、`/2` 取進位」取代自己「XOR 算輸出 + count≥2 算進位」兩條規則，變數從 5 個（`a,b,r,abCount,abXor`）精簡成 2 個（`sum,carry`）；其中一版還把「迴圈跑完後補最後進位」的特殊分支，改成把 `carry` 塞進迴圈繼續條件 `while(i>=0 || j>=0 || carry)`，讓收尾動作自然融入迴圈本身。

### 1️⃣ 語法概念

- `sum = a+b+carry; 輸出=sum%2; carry=sum/2` 可以取代「XOR 算輸出 + count of 1's 判斷進位」兩條規則，同一個算式同時算出輸出跟進位
- 兩個獨立指標各自從字串尾端（`size()-1`）遞減，可以取代「先整個 reverse 再用 index 正向存取」或「每次現算 `length()-i-1`」

### 2️⃣ 邏輯與複雜度

- O(max(n,m)) 時間、O(max(n,m)) 空間，是這題最優解
- 迴圈跑完後「若還有進位要多輸出一位」，可以把進位塞進迴圈繼續條件（`while (i>=0 || j>=0 || carry)`），不用另外寫收尾的 if 分支——把「特殊情況」變成「一般情況多跑一輪」

### 3️⃣ 演算法 / 資料結構盲點

- **迴圈裡的狀態變數管理，這次是最嚴重的一次**：`abCount`、`r` 宣告在迴圈內部，導致每輪都被重新初始化、跨輪讀到未定義的值。這是「該跨層共用卻宣告成區域變數」這個已經反覆出現的主要弱點的第 7 次出現，且是目前程度最重的一次（前幾次是覆蓋掉舊值，這次是直接讀到未初始化變數）
- 進位公式一開始又退回用 XOR 算，是同一次除錯過程裡「虛擬碼階段修正過的錯誤，程式碼階段又重新犯一次」，代表虛擬碼確認過的邏輯，轉成程式碼時要更小心逐行核對，不能默認轉譯不會出錯
- 變數數量本身也是一種盲點來源：習慣把每個中間值都拉出來命名（受 C# 維護習慣影響），但這題示範了「只在本輪迴圈內用完就丟的值，直接寫進算式比拉成變數更不容易出錯」——已整理進新概念卡 `digit_carry_addition.md`
