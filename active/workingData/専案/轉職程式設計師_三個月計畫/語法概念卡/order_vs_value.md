# 資料結構選擇框架：順序（Order）vs 數值（Value）

- 分類：解題思維框架（不綁定特定容器，選資料結構前先用這個篩選）
- 對應 C#：無直接語法對應，這是判斷邏輯，不是語法

> 這張卡不是某個容器的用法，是**選容器之前**要先問自己的問題。複習時先看 Q，自己講一遍答案，再點開 `<details>` 對答案。

## 自我測驗

<details>
<summary>Q1. 核心判斷原則是什麼？</summary>

A1. 陣列裡每個元素同時帶著兩種獨立資訊：**值是多少**、**出現在哪個位置/什麼時候發生**。資料結構只能選一種當整理依據。問自己：「這題的正確答案，會不會受『誰先誰後』影響？」

</details>

<details>
<summary>Q2. 為什麼「依值整理」的結構會丟掉順序？</summary>

A2. Hash Map、`map`（紅黑樹）、BST、排序，這些結構的存在目的就是「用值快速找到東西」，要做到這件事，必須依照值的大小（或 hash 結果）重新安排元素位置——這個「重新安排」的動作，就是順序資訊被丟掉的那一刻。之後沒辦法從結構反推回原始順序，除非額外把原始位置存成附加資料，但那樣要多一層「查完再驗證順序」的工作，複雜度反而更高。

</details>

<details>
<summary>Q3. 順序不重要 vs 順序重要，各自該往哪個方向想？</summary>

A3.
- **順序不重要**（答案跟誰先誰後無關，只在乎「存不存在」「值是什麼」）→ Hash Map / 排序類結構可以放心用，通常也最快
- **順序重要**（題目限制條件本身就跟「先後」有關：先買後賣、巢狀配對、子序列必須依序出現、結果也要維持排序）→ 用「原地保留順序」的做法：單一掃描、Stack（LIFO 天生保留順序）、雙指標

</details>

<details>
<summary>Q4. 已經刷過的題目怎麼對應到這個框架？</summary>

A4.

| 題目 | 順序重要嗎？ | 用的結構 | 為什麼 |
|------|------------|---------|--------|
| Two Sum | 不重要 | [Hash Map](unordered_map.md) | 只需要「存不存在」，不用管位置關係 |
| Valid Parentheses | **重要** | [Stack](stack.md) | LIFO 天生保留「發生順序」 |
| Merge Two Sorted Lists | **重要** | 雙指標，原地依序走訪（見 [linked_list.md](linked_list.md)） | 兩條輸入本身已排序，用雙指標延續順序，不重新排序 |
| Best Time to Buy/Sell Stock | **重要** | 單一掃描，邊走邊記錄最佳解 | 由左到右走一次，天生保留原始順序 |
| Valid Anagram | 不重要 | [Hash Map](unordered_map.md) | 只比字元計數是否一致，跟順序無關 |
| Binary Search | 不重要，但建置成本才是關鍵 | 二分法，不建輔助結構 | 單次查詢，Hash Map 的 O(n) 建置成本划不來，直接利用輸入已排序的性質 |

</details>

## 補充判斷：就算順序不重要，也要算「建置成本」划不划算

Hash Map 查詢是 O(1) 沒錯，但**建立** Hash Map 本身要 O(n)（掃過整個輸入一次）。如果題目只會查詢**一次**（不是同一份資料被反覆查詢很多次），這個 O(n) 建置成本沒辦法被攤提，會讓整體複雜度變成 O(n)，不是 O(1)。

Binary Search（242 Valid Anagram 之後的 704 Binary Search）就是活生生的例子：輸入已經排序好，直接用二分法完全不需要建立任何輔助結構，O(log n)；改用 Hash Map 反而要先花 O(n) 建表，整體變成 O(n)，比 O(log n) 慢，不符合題目要求。

判斷準則：**這份輸入本身有沒有已經具備、可以直接拿來利用的性質（已排序、已經是某種結構）？如果有，直接利用它往往比額外建一個新結構更省。** Hash Map 只有在「要花的建置成本能被之後的多次查詢攤提」時才划算。

## 完整筆記

延伸閱讀：「依值整理」這一家族的底層機制細節，見 [`unordered_map.md`](unordered_map.md)（hash table）、[`map.md`](map.md)（紅黑樹，原理在該卡「底層機制」章節）、[`binary_search.md`](binary_search.md)（排序陣列 + 二分法）——這些全部都是「犧牲順序、換取依值查詢效率」的同一種取捨。「保留順序」這一家族則見 [`stack.md`](stack.md)（LIFO）跟 [`linked_list.md`](linked_list.md)（雙指標、dummy head 尾端合併）。

拿到新題目時的檢查順序：
1. 先讀題目限制條件，有沒有「先...才能...」「依序」「子序列」「維持排序」這類字眼
2. 有 → 優先考慮單一掃描 / Stack / 雙指標，這些做法從頭到尾不重新排列元素
3. 沒有 → 再考慮 Hash Map / 排序類結構，通常效率更好
