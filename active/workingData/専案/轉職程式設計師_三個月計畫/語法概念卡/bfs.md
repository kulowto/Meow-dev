# BFS（廣度優先搜尋）與多起點 BFS

- 分類：解題思維框架（走訪順序）
- 對應 C#：語法上跟 C++ 一樣（`Queue<T>` 對應 `queue<T>`），差異在「什麼時候該想到用它」這個思考層面

> 複習時先看 Q，自己講一遍答案，再點開 `<details>` 對答案。
> 跟 [`recursion.md`](recursion.md)（DFS 常見用遞迴實作）是對照關係：DFS 往一個方向鑽到底才回頭，BFS 一批一批、按距離由近到遠往外擴散。跟 [`grid_traversal.md`](grid_traversal.md) 的 dx/dy 套路常常搭配使用。

## 自我測驗

<details>
<summary>Q1. 什麼時候該直覺想到用 BFS？</summary>

A1. 題目要求「每個節點/格子離某個起點（或某些起點）**最短距離**是多少」，且每一步的「移動成本」都相等（例如網格移動一步、圖上走一條邊）時，BFS 是強烈候選。BFS 天生保證「第一次走到某個節點時，走的路徑就是最短路徑」——因為它是一層一層往外擴散，不會有「先走了比較遠的路才發現有更近的路」這種情況（這點只在**每步成本相等**時成立，成本不相等要用 Dijkstra）。

</details>

<details>
<summary>Q2. 為什麼 DFS + 記憶化在這類「多節點互相依賴最短距離」的題目上行不通？</summary>

A2. DFS + 記憶化適合的情境是「子問題永遠比自己更小、不會反過來依賴自己」（例如 Climbing Stairs 的 `ways(n)` 只依賴 `ways(n-1)`、`ways(n-2)`，不會有 `ways(n-1)` 又反過來要用到 `ways(n)`）。但「找最短距離」這種題目，兩個相鄰、都還沒確定答案的節點可能**互相依賴**：A 要知道 B 的最小值才能算自己，B 也要知道 A 的最小值才能算自己，形成循環依賴，DFS 遞迴會在兩者之間無限繞圈，永遠沒有一方能先給出答案。BFS 用「按距離分層、由近到遠」的順序天生避開這個問題：計算某一層的節點時，永遠只依賴「上一層已經確定答案」的節點，不會出現互相等待的情況。

</details>

<details>
<summary>Q3. 「多起點 BFS」（multi-source BFS）跟一般單一起點 BFS 差在哪？核心語法怎麼寫？</summary>

A3. 差別只在**初始化階段**：一般 BFS 只把一個起點放進 queue；多起點 BFS 把**所有**起點一次性放進 queue，才開始展開。之後的展開邏輯完全一樣。

```cpp
queue<pair<int,int>> q;
vector<vector<int>> res(m, vector<int>(n, -1));   // -1 代表還沒走訪過

// 初始化：把所有起點一次放進 queue
for (int i = 0; i < m; i++)
    for (int j = 0; j < n; j++)
        if (mat[i][j] == 0) {
            res[i][j] = 0;
            q.push({i, j});
        }

int dx[] = {-1, 1, 0, 0};
int dy[] = {0, 0, -1, 1};

while (!q.empty()) {
    auto [r, c] = q.front();
    q.pop();                      // 每輪 while 只 pop 一次，pop 剛剛讀到的那個元素

    for (int d = 0; d < 4; d++) {
        int nr = r + dx[d];
        int nc = c + dy[d];
        if (nr < 0 || nr >= m || nc < 0 || nc >= n) continue;   // 超出邊界，跳過這個方向，不是跳出整個迴圈
        if (res[nr][nc] == -1) {
            res[nr][nc] = res[r][c] + 1;
            q.push({nr, nc});
        }
    }
}
```

</details>

<details>
<summary>Q4. 為什麼一定要把「所有」起點一次放進 queue 才開始展開，不能一個一個起點分開跑？</summary>

A4. 如果分開跑（先展開起點 A 的所有層，再展開起點 B 的所有層），某個格子可能先被起點 A 走到、記錄了一個較大的距離，但其實從起點 B 走過去更近，等到 B 開始展開時，這個格子已經被標記成「走訪過」（不是 `-1` 了），不會再被更新，得到錯誤的、偏大的答案。**所有起點必須同時放進 queue、同時展開**，才能保證每個格子第一次被走到時，走的就是離「所有起點中最近的那一個」的最短距離。

</details>

<details>
<summary>Q5. 常見的坑是什麼？</summary>

A5.
1. **`que.front()` 讀取跟 `que.pop()` 移除是兩個獨立動作**：`front()` 只是「看一眼」，不會把元素拿掉；忘記呼叫 `pop()`，或把 `pop()` 錯放到會被呼叫不只一次的地方（例如放在內層 for 迴圈裡，每個方向都呼叫一次），會導致佇列裡的元素被清空的次數跟預期對不上，甚至造成無窮迴圈（一直讀到同一個沒被移除的元素）
2. **邊界判斷用 `continue` 還是 `break`**：某一個方向超出邊界時，該做的是跳過**這一個方向**、繼續檢查其他方向（`continue`），不是直接跳出整個 for 迴圈（`break`）——用 `break` 會讓後面還沒檢查的方向全部被跳過
3. **邊界判斷的比較符號**：合法索引範圍是 `0` 到 `size-1`，判斷「超出範圍」要用 `>= size`，不是 `> size`（差一個索引，會讓剛好等於 `size` 的非法索引被誤判成合法，導致存取到不存在的位置）

</details>

## 完整筆記

BFS 用 queue 實作，天生符合「先進先出」的展開順序，保證了「同一層的節點，都是從上一層已經確定答案的節點展開出來的」這個關鍵性質——這正是「最短距離第一次被寫入就已經是最終答案，不需要事後覆蓋」的原因所在。
