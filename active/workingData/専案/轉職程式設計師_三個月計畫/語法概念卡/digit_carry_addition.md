## 自我測驗

<details>
<summary>Q1. 逐位相加（個位、二進位…）要算「這一位輸出什麼」跟「要不要進位」時，有沒有比「XOR + 判斷是否≥某個門檻」更簡單的寫法？</summary>

A1. 直接把這一位所有要加總的值（例如二進位的 `a位, b位, 進位carry`）**當成數字加起來**，不要拆成「XOR 算輸出」「count of 1's 算進位」兩條不同規則：

```cpp
int sum = a位 + b位 + carry;
int 這一位輸出 = sum % 2;   // 取餘數
carry = sum / 2;             // 取商，就是要往下一位傳的進位
```

原理：`sum` 在二進位情境下最大是 3（`1+1+1`），`%2` 剛好對應「這一位滿 2 進 1」的規則，`/2` 剛好對應「進位的量」。十進位加法也是同一招（只是換成 `%10`、`/10`）。

</details>

<details>
<summary>Q2. 迴圈跑完之後，如果「最後可能還留一個進位沒輸出」，要怎麼處理才不用另外寫特殊分支？</summary>

A2. 把「進位」直接塞進迴圈的**繼續條件**，而不是跑完固定次數後再額外判斷一次：

```cpp
while (i >= 0 || j >= 0 || carry) {
    int sum = carry;
    if (i >= 0) sum += a[i--] - '0';
    if (j >= 0) sum += b[j--] - '0';
    ans.push_back(sum % 2 + '0');
    carry = sum / 2;
}
```

只要還有數字沒處理完、或是手上還有進位沒處理掉，就繼續跑一輪——最後多出來的進位會自然被迴圈的最後一輪、用同一套邏輯處理掉，不需要跑完迴圈後另外寫 `if (還有進位) { 補一位 }` 這種特殊分支。**任何「處理完主要輸入後，可能還有一個收尾動作」的情境**（不只是進位，其他累加/結轉類問題也常有這種模式），都可以想一下能不能把收尾動作塞進迴圈條件本身。

</details>

<details>
<summary>Q3. 想用兩個指標從字串尾端往前走，需不需要先把字串整個 reverse 過？</summary>

A3. 不需要。用兩個各自獨立的索引（例如 `i = a.size()-1`, `j = b.size()-1`），每次用完各自 `i--`、`j--`，就能從尾端開始各自往前走，天然處理兩個字串長度不同的情況，不用先花一次 O(n) reverse、也不用每次計算 `length()-i-1` 這種索引運算。

</details>

<details>
<summary>Q4. 什麼時候該把中間值拉出來宣告成獨立變數？什麼時候不用？</summary>

A4. 判斷準則：**這個值，有沒有離開「這一次迴圈/這一段邏輯」的範圍還會被用到？**

- **沒有**（只在這一輪迴圈內部算完就丟掉，下一輪重新算）→ 直接寫成算式的一部分（例如 `sum % 2`），不用額外命名一個變數。變數越多，要自己心智追蹤「這個變數該不該跨輪保留、宣告位置對不對、賦值順序對不對」的負擔就越重——這正是容易踩坑的地方（宣告在迴圈內部卻想跨輪共用、或忘記在該重置的時候重置）
- **有**（例如進位 `carry` 真的要從這一輪傳到下一輪）→ 才需要拉出來當一個獨立變數，且要特別小心它的**宣告位置**（必須在迴圈外面，不能每輪重新宣告）跟**初始化時機**

C# 或一般專案維護情境下，拉變數出來還有額外的合理理由：這個值之後真的會被多處重複使用、除錯時想在中間插斷點檢查、或邏輯複雜到需要變數名稱本身輔助理解。但 LeetCode 這種一次性、獨立函式的情境，這些理由通常不成立，精簡（少變數、算術合併）會比較好維護。

</details>

## 完整筆記

這兩個技巧本質上是同一件事的兩面：**能把邏輯收斂成單一算式或單一迴圈條件時，就不要拆成多個變數 + 多個分支**。分支跟變數越多，狀態要追蹤的地方就越多，越容易在「該更新卻沒更新」「該重置卻沒重置」「該跨輪共用卻宣告錯位置」這幾類問題上出錯。
